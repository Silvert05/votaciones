Portar las fórmulas de días al método optimizado moficarRubroRolOptimizado

Objetivo: adaptar la lógica de cálculo que hoy vive en Java (reCalcularNomina → importarRubro / despejarFormulasRol) a la nueva arquitectura basada en SQL en base de datos que usa moficarRubroRolOptimizado → reCalcularRolOptimizado.

Clases:

  • nexsys-war/src/java/paq_nomina/pre_rol.java → moficarRubroRolOptimizado() (línea 1574)
  • nexsys-ejb/src/java/paq_nomina/ejb/ServicioNomina.java → reCalcularRolOptimizado(...) (línea 6608)

Convención asumida (confirmada): el SQL dinámico de nrh_importados.sql_nrhimp recibe los parámetros de forma posicional: $1 = ide_geedp, $2 = ide_gepro (vía EXECUTE ... USING ide_geedp, ide_gepro dentro de ejecutar_sql_dinamico).

1. Cómo cambia la arquitectura

Modelo viejo (reCalcularNomina) — cálculo en Java, fila por fila 

por cada empleado:
  por cada rubro:
    IMPORTADO  → importarRubro()  (gran switch Java: días, RMU, anticipos…)   → 1 UPDATE
    FÓRMULA    → guarda "=…", luego despejarFormulasRol() lo evalúa en Java   → 1 UPDATE

Cientos de SELECT/UPDATE individuales por empleado.

Modelo nuevo (reCalcularRolOptimizado) — cálculo en BD, por lotes 

Paso 1: updateRubrosTipoConstante()  → 1 UPDATE masivo (ide_nrfoc = 3)
Paso 2: updateRubrosTipoImportado()  → 1 UPDATE masivo (ide_nrfoc = 2)
        cada importado se resuelve con: ejecutar_sql_dinamico(sql_nrhimp, ide_geedp, ide_gepro)
        donde sql_nrhimp viene de la tabla nrh_importados (parametro_nrhimp = formula_nrder)
Paso 3: getRubrosFormula() + getRubrosByFormula()  → fórmulas (ide_nrfoc = 0)
        la sustitución de [ide_nrder]/sum() la hace la función SQL calcular_formula()
        Java solo llama evaluarExpresion() sobre la fórmula ya numérica
Concepto Viejo (Java) Nuevo (SQL)
Rubro CONSTANTE valor fijo en memoria updateRubrosTipoConstante (cast formula_nrder::numeric)
Rubro IMPORTADO (días, RMU…) importarRubro() switch fila en nrh_importados con sql_nrhimp ejecutado por ejecutar_sql_dinamico
Reemplazo de fórmulas getFormulaReemplazada() (parser Java) función SQL calcular_formula()
Evaluación aritmética evaluarExpresion() sigue en Java (evaluarExpresion)
Nº de sentencias N×M individuales 3 lotes + 1 por rubro fórmula

Conclusión: para "aplicar las fórmulas de días" al método nuevo, cada rubro de días deja de ser código Java y pasa a ser una fila en nrh_importados cuyo sql_nrhimp calcula el valor a partir de $1 = ide_geedp y $2 = ide_gepro.

Bloque común para obtener NRO_DIAS_COMERCIAL_NRTIT (días comerciales del tipo de rol) 

SELECT tir.nro_dias_comercial_nrtit::int
FROM nrh_detalle_rol dro
JOIN nrh_rol rol               ON rol.ide_nrrol = dro.ide_nrrol
JOIN nrh_detalle_tipo_nomina dtn ON dtn.ide_nrdtn = rol.ide_nrdtn
JOIN nrh_tipo_rol tir          ON tir.ide_nrtit = dtn.ide_nrtit
WHERE dro.ide_geedp = $1 AND rol.ide_gepro = $2
LIMIT 1

INSERT INTO nrh_importados (parametro_nrhimp, sql_nrhimp) VALUES (

3.3 Días trabajados (al mes) — lógica de nómina NORMAL 

INSERT INTO nrh_importados (parametro_nrhimp, sql_nrhimp) VALUES (
'DIAS_TRABAJADOS',
$SQL$
WITH p AS (SELECT fecha_inicial_gepro AS fi, fecha_final_gepro AS ff
           FROM gen_perido_rol WHERE ide_gepro = $2),
     e AS (SELECT fecha_geedp AS fc
           FROM gen_empleados_departamento_par WHERE ide_geedp = $1),
     c AS (SELECT tir.nro_dias_comercial_nrtit::int AS ndc
           FROM nrh_detalle_rol dro
           JOIN nrh_rol rol               ON rol.ide_nrrol = dro.ide_nrrol
           JOIN nrh_detalle_tipo_nomina dtn ON dtn.ide_nrdtn = rol.ide_nrdtn
           JOIN nrh_tipo_rol tir          ON tir.ide_nrtit = dtn.ide_nrtit
           WHERE dro.ide_geedp = $1 AND rol.ide_gepro = $2 LIMIT 1)
SELECT CASE
  WHEN e.fc IS NULL THEN 0
  WHEN date_trunc('month', e.fc) = date_trunc('month', p.ff) THEN
       LEAST(
         (make_date(EXTRACT(YEAR FROM p.ff)::int, EXTRACT(MONTH FROM p.ff)::int, 30)::date
          - e.fc::date) + 1,
         c.ndc)
  ELSE c.ndc
END::numeric
FROM p, e, c
$SQL$
);

(Si ingresó en el mes del rol → días proporcionales con tope = días comerciales; si no, mes comercial completo. La variante de liquidación del Java —que usa FECHA_LIQUIDACION_GEEDP y getDiferenciasDeFechas(fecha_inicial, fecha_contrato)+1— se modela como un parámetro aparte si la nómina optimizada procesa liquidaciones; ver §5.)

3.4 Días subrogados 

INSERT INTO nrh_importados (parametro_nrhimp, sql_nrhimp) VALUES (
'DIAS_SUBROGADOS',
$SQL$
WITH p AS (SELECT fecha_inicial_gepro AS fi FROM gen_perido_rol WHERE ide_gepro = $2),
     e AS (SELECT fecha_encargo_geedp AS fs, fecha_encargo_fin_geedp AS ffs
           FROM gen_empleados_departamento_par WHERE ide_geedp = $1),
     c AS (SELECT tir.nro_dias_comercial_nrtit::int AS ndc
           FROM nrh_detalle_rol dro
           JOIN nrh_rol rol               ON rol.ide_nrrol = dro.ide_nrrol
           JOIN nrh_detalle_tipo_nomina dtn ON dtn.ide_nrdtn = rol.ide_nrdtn
           JOIN nrh_tipo_rol tir          ON tir.ide_nrtit = dtn.ide_nrtit
           WHERE dro.ide_geedp = $1 AND rol.ide_gepro = $2 LIMIT 1)
SELECT CASE
  WHEN e.fs IS NULL OR e.ffs IS NULL THEN 0
  -- la subrogación INICIA en el mes del rol
  WHEN date_trunc('month', e.fs) = date_trunc('month', p.fi) THEN
       CASE WHEN date_trunc('month', e.ffs) = date_trunc('month', p.fi)
            THEN (e.ffs::date - e.fs::date) + 1
            ELSE (make_date(EXTRACT(YEAR FROM p.fi)::int, EXTRACT(MONTH FROM p.fi)::int, 30)::date
                  - e.fs::date) + 1
       END
  -- la subrogación EMPEZÓ antes del mes del rol
  ELSE
       CASE WHEN date_trunc('month', e.ffs) = date_trunc('month', p.fi)
            THEN (e.ffs::date - make_date(EXTRACT(YEAR FROM p.fi)::int, EXTRACT(MONTH FROM p.fi)::int, 1)::date) + 1
            WHEN date_trunc('month', p.fi) < date_trunc('month', e.ffs)
            THEN c.ndc            -- la subrogación cubre todo el mes
            ELSE 0
       END
END::numeric
FROM p, e, c
$SQL$
);

(Calcula los días de encargo que caen dentro del mes del rol según el solapamiento [inicio, fin]. La condición final usa comparación de mes/año completa con date_trunc, que corrige la comparación parcial mes_rol < mes_fin_sub del Java.)

3.6 Días fondos de reserva 

INSERT INTO nrh_importados (parametro_nrhimp, sql_nrhimp) VALUES (
'DIAS_FONDOS_RESERVA',
$SQL$
WITH p AS (SELECT fecha_final_gepro AS ff FROM gen_perido_rol WHERE ide_gepro = $2),
     e AS (SELECT edp.fecha_geedp AS fc, emp.fecha_ingreso_gtemp AS fi
           FROM gen_empleados_departamento_par edp
           JOIN gth_empleado emp ON emp.ide_gtemp = edp.ide_gtemp
           WHERE edp.ide_geedp = $1),
     c AS (SELECT tir.nro_dias_comercial_nrtit::int AS ndc
           FROM nrh_detalle_rol dro
           JOIN nrh_rol rol               ON rol.ide_nrrol = dro.ide_nrrol
           JOIN nrh_detalle_tipo_nomina dtn ON dtn.ide_nrdtn = rol.ide_nrdtn
           JOIN nrh_tipo_rol tir          ON tir.ide_nrtit = dtn.ide_nrtit
           WHERE dro.ide_geedp = $1 AND rol.ide_gepro = $2 LIMIT 1),
     v AS (SELECT e.fc, e.fi, p.ff, c.ndc,
                  (p.ff::date - e.fi::date) AS dias_antig
           FROM p, e, c)
SELECT CASE
  WHEN fc IS NULL THEN 0
  WHEN dias_antig > 360 AND dias_antig <= 395
       AND EXTRACT(MONTH FROM ff) = EXTRACT(MONTH FROM fc) THEN
       LEAST(
         (make_date(EXTRACT(YEAR FROM ff)::int, EXTRACT(MONTH FROM ff)::int, 30)::date
          - make_date(EXTRACT(YEAR FROM ff)::int, EXTRACT(MONTH FROM fc)::int, EXTRACT(DAY FROM fc)::int)::date) + 1,
         30)
  ELSE ndc
END::numeric
FROM v
$SQL$
);

(Solo cuenta días desde el aniversario del contrato cuando el empleado cumple su primer año —antigüedad >360 y ≤395— en el mes del rol, con tope 30; en otro caso, mes comercial completo.)

3.7 Días acumulados 

INSERT INTO nrh_importados (parametro_nrhimp, sql_nrhimp) VALUES (
'DIAS_ACUMULADOS',
$SQL$
WITH vdt AS (
  SELECT COALESCE(SUM(dro.valor_nrdro), 0)::numeric AS v
  FROM nrh_detalle_rol dro
  JOIN nrh_rol rol         ON rol.ide_nrrol = dro.ide_nrrol
  JOIN nrh_detalle_rubro der ON der.ide_nrder = dro.ide_nrder
  WHERE rol.ide_gepro = $2
    AND der.ide_nrrub = <<ID_RUBRO_DIAS_TRABAJADOS>>
    AND dro.ide_geedp IN (
        SELECT ide_geedp FROM gen_empleados_departamento_par
        WHERE ide_gtemp = (SELECT ide_gtemp FROM gen_empleados_departamento_par WHERE ide_geedp = $1)
          AND ide_gttem <> 3)
)
SELECT CASE
  WHEN 368 = v OR (368 > 360 AND v = 360) THEN v   -- diasAntiguedad HARDCODE = 368 (igual que el Java)
  WHEN 368 > v AND 368 <= 360            THEN 368  -- rama inalcanzable (368 <= 360 = false)
  WHEN 368 > 360 AND v < 360             THEN 360
  ELSE 0
END::numeric
FROM vdt
$SQL$
);

⚠ Replica fielmente el diasAntiguedad = 368 hardcodeado del método Java getDiasAcumulados (línea 1464). El cálculo real por fechas está comentado en el original. Recomendación: si se desea habilitar la antigüedad real, reemplazar 368 por
(SELECT (pro.fecha_final_gepro::date - emp.fecha_ingreso_gtemp::date) FROM ... ) usando fecha_ingreso_grupo_gtemp. Ver §5.

5. Cambios de código y bloqueos a resolver

Para que moficarRubroRolOptimizado calcule correctamente con estas fórmulas, hay que corregir el lado Java/SQL:

5.1 🔴 BLOQUEANTE — getRubrosFormula filtra un solo rubro (línea 6518) 

WHERE ide_nrfoc = 0 and ide_nrdtn=... and activo_nrder=true and ide_nrder=966 --and ide_nrder=951

El and ide_nrder=966 está hardcodeado de pruebas: el Paso 3 solo evalúa el rubro 966. Debe eliminarse para procesar todos los rubros de tipo fórmula:

WHERE ide_nrfoc = 0 AND ide_nrdtn = <ide_nrdtn> AND activo_nrder = true
ORDER BY ORDEN_NRDER ASC;

5.2 🟠 reCalcularRolOptimizado tiene System.out.println de depuración (líneas 6620-6626)

Quitarlos antes de producción (impactan rendimiento en lotes grandes).

5.3 🟠 Pasos del modelo viejo que el optimizado NO replica

reCalcularNomina hacía además, y reCalcularRolOptimizado no:

  • Desactivar amortizaciones del período (update NRH_AMORTIZACION ... ACTIVO_NRAMO=false) y reasignarlas (IDE_NRROL).
  • Insertar rubros faltantes (INSERT INTO NRH_DETALLE_ROL de detalles no creados).
  • Actualizar estado del rol: ESTADO_RENTA_NRROL y ESTADO_CALCULADO_NRROL.
  • Eliminar detalles de rubros inactivos/duplicados.

Decidir si estos pasos se ejecutan en otro punto (al generar el rol) o deben añadirse al flujo optimizado. Si no se replican, los anticipos y el estado del rol quedarán inconsistentes tras el recálculo.

5.4 🟢 Ya cubierto en moficarRubroRolOptimizado

El tratamiento de jubilación por invalidez (encerrarValoresRol, sumarRubrosJubilacionXInvalidacion, actualizarRubrosIessPersonalXJubilacionXInvalidacion) ya está presente en el método optimizado (pre_rol.java, líneas 1601-1603) — no requiere cambios.

5.5 Orden de los rubros importados

updateRubrosTipoImportado ordena ORDEN_NRDER DESC. Verificar que ningún rubro importado dependa de otro importado calculado después (los importados de días son independientes entre sí salvo días acumulados, que lee el valor ya guardado de días trabajados → días trabajados debe estar persistido antes; con el UPDATE masivo único esto puede no cumplirse en la misma pasada → ver nota).

⚠ Dependencia días acumulados → días trabajados: en el modelo viejo, "días trabajados" se calculaba e insertaba antes de que "días acumulados" lo sumara. En el UPDATE masivo del Paso 2 ambos se resuelven en la misma sentencia, por lo que "días acumulados" podría leer el valor_nrdro anterior de días trabajados. Opciones: (a) ejecutar updateRubrosTipoImportado en dos fases (primero días trabajados, luego el resto), o (b) que el sql_nrhimp de DIAS_ACUMULADOS recalcule los días trabajados en línea en lugar de leer valor_nrdro.
